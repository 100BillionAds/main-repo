# 운영 안내서

서비스가 잘 돌고 있는지 확인하는 방법, 문제가 생겼을 때 볼 곳, 실제 돈을 받기 전에 해야 할 일을 정리합니다.

## 지금 구성 (무료)

| 부품 | 서비스 | 무료 플랜의 제약 |
|---|---|---|
| 웹 서버 + 워커 | Render Web Service (`tenbadv`) | 15분간 요청이 없으면 잠듦 (다음 첫 요청 50초~1분). 메모리 512MB. 월 750시간 |
| DB | TiDB Cloud Starter | 저장 5GiB, 자동 백업은 하루 1회·보관 1일, 특정 시점 복구 없음 |
| Redis | Render Key Value (`tenbadv-cache`) | 재시작하면 데이터가 사라짐 |
| 예약 작업 | 서버 내장 스케줄러 + GitHub Actions | 서버가 잠들면 내장 스케줄러도 멈춤 |

## 상태 확인

| 주소 | 의미 | 쓰는 곳 |
|---|---|---|
| `GET /api/health` | 프로세스가 살아 있는가. DB·Redis 는 확인하지 않음 | Render·Docker 헬스 체크 |
| `GET /api/health/ready` | DB, 마이그레이션, Redis, 이벤트 처리가 정상인가 | 사람, 외부 모니터링 |

`/api/health/ready` 응답 읽는 법:

```json
{
  "status": "ok",
  "checks": {
    "database":   { "status": "ok", "latencyMs": 12 },
    "migrations": { "status": "ok", "applied": 4 },
    "redis":      { "status": "ok", "latencyMs": 3 },
    "outbox":     { "status": "ok", "pending": 0, "stale": 0, "dead": 0 }
  }
}
```

| 전체 상태 | HTTP | 뜻 |
|---|---|---|
| `ok` | 200 | 모두 정상 |
| `degraded` | 200 | DB 는 정상이지만 일부가 비정상. 서비스는 동작함 |
| `down` | 503 | DB 에 닿지 않음. 서비스가 일할 수 없음 |

| 항목 | 비정상일 때 | 영향 | 조치 |
|---|---|---|---|
| `database: down` | DB 접속 실패 | 전체 장애 | TiDB Cloud 콘솔에서 인스턴스 상태, Render 의 `DATABASE_URL` 확인 |
| `migrations: degraded` | 적용 안 된 마이그레이션이 있거나 체크섬 불일치 | 새 기능이 실패할 수 있음 | 서버 로그의 `데이터베이스 마이그레이션 실패` 확인 → [MIGRATIONS.md](./MIGRATIONS.md) |
| `redis: down` | Redis 접속 실패 | 캐시 없음, 요청 제한이 서버별로 느슨해짐, 이벤트는 즉시 처리로 전환 | Render 의 `tenbadv-cache` 상태 확인. 급하지 않음 |
| `redis: disabled` | `REDIS_URL` 없음 | 위와 같음 (정상적인 구성일 수 있음) | |
| `outbox.stale > 0` | 15분 넘게 처리 안 된 이벤트 | 알림이 늦어지고 있음 | 서버 로그의 `이벤트 처리 실패` 확인 → [EVENTS.md](./EVENTS.md) |
| `outbox.dead > 0` | 10회 실패해 포기한 이벤트 | 그 알림은 나가지 않음 | 원인을 고친 뒤 `attempts` 를 0 으로 되돌림 ([EVENTS.md](./EVENTS.md#운영-점검)) |

> **왜 주소가 둘인가**: 플랫폼 헬스 체크에 `/ready` 를 쓰면, Redis 가 잠깐 끊겼을 때 플랫폼이 멀쩡한 서버를 "죽었다"고 보고 재시작합니다. 작은 장애가 큰 장애가 됩니다. 그래서 플랫폼에는 "살아 있는가"만 알려 줍니다.

## 서버 로그에서 찾을 것

Render → tenbadv → Logs 에서 검색합니다.

| 검색어 | 뜻 |
|---|---|
| `마이그레이션 N건 적용` | 배포 때 스키마가 바뀜 (정상) |
| `데이터베이스 마이그레이션 실패` | 스키마 변경 실패. 바로 확인 |
| `이벤트 처리 시작 (큐 워커` | Redis 로 큐가 동작 중. `(즉시 처리` 면 Redis 없이 동작 중 |
| `이벤트 처리 실패` | 알림 등 후속 작업 실패. 자동 재시도됨 |
| `자동정산:` | 자동 구매확정·자동 취소가 실행됨 |
| `자동정산 실패`, `자동 구매확정 실패` | 정산 오류. 바로 확인 |
| `포트원 결제 조회 실패` | 결제 검증 실패. `status: 401` 이면 `PORTONE_API_SECRET` 문제 |
| `Redis 연결 오류`, `캐시 오류` | Redis 문제. 서비스는 계속 동작 |
| `LLM { type: 'retry'` / `'fallback'` | AI 제공자 일시 장애로 재시도·대체 |

## 예약 작업

| 작업 | 주기 | 실행 주체 | API |
|---|---|---|---|
| 자동정산 (자동 구매확정·자동 취소) | 10분 | 서버 내장 스케줄러 | `POST /api/cron/settle` |
| 〃 (서버가 잠들었을 때 깨워서 실행) | 1시간 | GitHub Actions `settle` | 〃 |
| 이벤트 릴레이 | 30초 + 거래 직후 | 서버 (`eventBus`) | — |
| 정리 (오래된 이벤트·알림·AI 기록 삭제) | 하루 | 서버 내장 스케줄러, GitHub Actions | `POST /api/cron/maintenance` |

두 API 는 `Authorization: Bearer $CRON_SECRET` 또는 관리자 로그인이 필요합니다.

**GitHub Actions 가 동작하려면** 저장소 Settings → Secrets and variables → Actions 에 Secret `CRON_SECRET` (Render 의 값과 동일) 이 있어야 합니다. 없으면 서버가 잠든 동안 자동정산이 돌지 않습니다.

### 정리 작업이 지우는 것

| 대상 | 기준 |
|---|---|
| 처리 끝난 이벤트 (`outbox_events`) | 처리 후 30일 |
| 읽은 알림 (`notifications`) | 읽은 뒤 90일 |
| AI 사용 기록 (`ai_requests`) | 180일 |

처리되지 않은 이벤트와 안 읽은 알림은 오래돼도 지우지 않습니다. 거래·포인트·결제 기록은 지우지 않습니다.

## 모니터링 붙이기 (권장)

외부 가동 시간 모니터(UptimeRobot, Better Stack 등의 무료 플랜)에 아래를 등록하면 장애를 메일로 받습니다.

| 주소 | 주기 | 알림 조건 |
|---|---|---|
| `https://tenbadv.onrender.com/api/health/ready` | 5분 | 응답 없음, 503, 또는 본문에 `"status":"ok"` 가 없음 |

부수 효과: 5분마다 요청이 오므로 **무료 서버가 잠들지 않습니다.** 내장 스케줄러와 워커가 계속 돕니다. 월 750시간 한도(31일 × 24시간 = 744시간) 안에 들어옵니다.

## 백업과 복구

| 항목 | 현재 (무료) |
|---|---|
| 자동 백업 | TiDB Cloud 가 하루 1회 |
| 보관 기간 | **1일** |
| 특정 시점 복구 | 없음 |
| 복구 방식 | 백업 스냅샷을 새 인스턴스로 복구한 뒤 `DATABASE_URL` 을 바꿈 |

즉 "어제 상태"로만 돌아갈 수 있고, 이틀 전 실수는 되돌릴 수 없습니다. 실제 거래 데이터가 쌓이기 시작하면 부족합니다.

- **수동 내보내기**: TiDB Cloud 콘솔 → 인스턴스 → Data → Export 로 SQL/CSV 파일을 내려받을 수 있습니다. 큰 변경 전에 받아 두세요.
- **보관 기간 늘리기**: 사용 한도(spending limit)를 0 보다 크게 설정하면 최대 30일까지 보관할 수 있습니다 (과금 가능).
- 내보낸 파일에는 회원 정보가 들어 있습니다. 공개 저장소나 공유 드라이브에 올리지 마세요.

Redis 는 백업하지 않습니다. 사라져도 되는 데이터만 둡니다 ([REDIS.md](./REDIS.md)).

## 배포와 되돌리기

- `main` 에 병합 → CI 통과 → Render 가 자동 배포합니다.
- 배포 때 서버는 종료 신호를 받고, 처리 중이던 요청과 이벤트를 마친 뒤(최대 10초) 내려갑니다.
- **되돌리기**: Render → tenbadv → Deploys → 이전 배포의 Rollback. 단, 새 배포가 마이그레이션을 적용했다면 이전 코드는 `MISSING_MIGRATION` 을 로그에 남깁니다. 테이블·컬럼을 "추가"만 하는 마이그레이션이면 이전 코드도 그대로 동작합니다. 삭제·이름 변경이 있었다면 되돌리기 전에 [MIGRATIONS.md](./MIGRATIONS.md) 를 확인하세요.

## 비밀값

| 값 | 위치 | 바꿀 때 |
|---|---|---|
| `DATABASE_URL` | Render | TiDB 에서 비밀번호 재설정 후 교체 |
| `NEXTAUTH_SECRET` | Render | 바꾸면 모든 사용자가 로그아웃됨 |
| `CRON_SECRET` | Render + GitHub Secret | 두 곳을 같이 바꿈 |
| `PORTONE_API_SECRET` | Render | 포트원 콘솔에서 재발급 |
| `ANTHROPIC_API_KEY` / `OPENAI_API_KEY` | Render | 각 콘솔에서 재발급 |

비밀값은 코드·PR·채팅·이슈에 적지 않습니다. 유출이 의심되면 바로 재발급합니다.

## 테스트 계정 정리

운영 DB 에 검증용 계정(`e2ebuyer…`, `e2edes…`, `e2eadmin…`)이 있다면, **공개 운영 전에 삭제하거나 비밀번호를 바꾸세요.** 특히 관리자 권한을 가진 테스트 계정은 그대로 두면 안 됩니다.

```sql
-- 관리자 권한 회수
UPDATE users SET role = 'user' WHERE username LIKE 'e2eadmin%';
-- 또는 삭제 (연결된 거래·알림 등이 함께 지워집니다)
DELETE FROM users WHERE username LIKE 'e2e%';
```

## 실제 돈을 받기 전에

지금은 포트원 **테스트 채널**이라 실제 결제가 일어나지 않습니다. 실제 운영으로 넘어가려면 기술 외의 준비가 필요합니다. 아래는 확인할 항목의 목록이며 법률 자문이 아닙니다. 실제 진행 전에 전문가(변호사, 세무사)와 PG사에 확인하세요.

| 항목 | 내용 |
|---|---|
| 사업자 등록, 통신판매업 신고 | 온라인으로 대가를 받고 거래를 중개하려면 필요 |
| PG 계약 | 포트원 실연동 채널은 PG사 심사·계약 후 발급 |
| 포인트(선불 충전금) | 충전해 두고 쓰는 포인트를 발행·환급하는 구조는 전자금융거래법상 선불전자지급수단 규제 대상이 될 수 있음. 발행 규모·사용처에 따라 등록 의무가 달라지므로 확인 필요 |
| 에스크로(결제대금 예치) | 구매자의 돈을 플랫폼이 보관했다가 정산하는 구조. 직접 보관하지 않고 PG사의 에스크로·정산 대행 서비스를 쓰는 방법이 일반적 |
| 출금(포인트 → 현금) | 실제 송금이 일어남. 본인 확인, 세금(원천징수 등) 처리 필요 |
| 약관, 개인정보 처리방침 | 환불·분쟁 기준, 수수료, 수집하는 개인정보 고지 |
| 통신판매중개자 고지 | 플랫폼이 거래 당사자가 아님을 알리는 표시 |

기술 쪽 점검:

- [ ] 테스트 계정 삭제, 본인 계정만 관리자
- [ ] 포트원 실연동 채널 키로 교체, 결제 웹훅 연결 (지금은 브라우저가 검증을 요청하는 방식만 있음)
- [ ] 유료 플랜: 잠들지 않는 서버, 백업 보관 기간 연장, 데이터가 유지되는 Redis
- [ ] 워커를 별도 프로세스로 분리
- [ ] 외부 모니터링과 오류 알림
- [ ] 출금 기능의 실제 송금 연동과 관리자 승인 절차 검토
