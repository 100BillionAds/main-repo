# 이벤트와 메시지 큐

거래에서 일어난 일을 **이벤트**로 남기고, 알림 같은 후속 작업을 **큐**로 넘겨 따로 처리하는 구조를 설명합니다.

## 왜 필요한가

구매확정이 되면 정산 외에도 할 일이 생깁니다: 디자이너에게 알림, 구매자에게 알림, 앞으로는 메일이나 통계.

이것을 정산 코드 안에 차례로 넣으면 문제가 생깁니다.

| 문제 | 설명 |
|---|---|
| 느려진다 | 사용자는 알림·메일 발송이 끝날 때까지 기다린다 |
| 같이 실패한다 | 알림이 실패하면 정산을 롤백할 것인가? 정산과 무관한 장애가 돈의 흐름을 막는다 |
| 계속 고쳐야 한다 | 후속 작업을 하나 붙일 때마다 정산 코드를 수정한다 |

그래서 정산은 **"거래가 완료됐다"는 사실만 남기고 끝냅니다.** 후속 작업은 그 사실을 듣고 각자 따로 합니다.

## 용어

| 용어 | 뜻 |
|---|---|
| 도메인 이벤트 | 업무에서 일어난 일을 과거형으로 적은 기록. 예: `trade.completed` |
| 생산자 / 소비자 | 이벤트를 만드는 쪽 / 듣고 일하는 쪽 |
| 아웃박스(outbox) | 보낼 이벤트를 먼저 적어 두는 DB 테이블 |
| 릴레이(relay) | 아웃박스의 이벤트를 큐로 옮기는 일 |
| 메시지 큐 | 할 일 목록. 넣는 쪽은 넣고 바로 돌아가고, 워커가 꺼내 처리한다 |
| 워커 | 큐에서 일을 꺼내 처리하는 실행 단위 |
| 적어도 한 번(at-least-once) | 유실은 없지만 같은 것이 두 번 올 수 있는 전달 보장 |
| 멱등(idempotent) | 같은 일을 두 번 해도 결과가 한 번 한 것과 같음 |

## 전체 흐름

```
① 업무 트랜잭션 (escrowService)
   ┌──────────────────────────────────────────────┐
   │ 거래 상태 변경 + 포인트 이동 + outbox_events 기록 │  ← 한 트랜잭션. 함께 커밋되거나 함께 롤백
   └──────────────────────────────────────────────┘
                     │ 커밋 직후 릴레이를 깨움 (+ 30초마다, 서버 시작 시)
                     ▼
② 릴레이 (eventBus.relayOutbox)
   보낼 이벤트를 "내 것"으로 표시하고 가져온다
                     │
        ┌────────────┴─────────────┐
   Redis 있음                   Redis 없음 / 큐 장애
        ▼                          ▼
③ 큐 (BullMQ) ──▶ 워커        그 자리에서 바로 처리
        └────────────┬─────────────┘
                     ▼
④ 소비자 (알림): notifications 에 기록 → outbox_events.processed_at 표시
```

## 아웃박스: 왜 큐에 바로 넣지 않나

"DB 를 바꾸고 + 큐에 알린다"는 서로 다른 두 시스템에 걸친 작업이라 한 번에 성공시킬 수 없습니다.

| 순서 | 사고 |
|---|---|
| DB 커밋 → 큐 전송 실패 | 정산은 됐는데 아무도 모른다 (알림 누락) |
| 큐 전송 → DB 롤백 | 일어나지 않은 일의 알림이 나간다 |

**이벤트를 큐가 아니라 같은 DB 의 테이블에 먼저 적습니다.** 업무 변경과 한 트랜잭션이므로 둘은 반드시 함께 커밋되거나 함께 롤백됩니다. 큐로 옮기는 일은 그 뒤에, 될 때까지 다시 합니다.

`outbox_events` 가 이벤트의 **원본**입니다. 운영의 무료 Redis 는 재시작하면 데이터가 사라지지만, 큐가 통째로 날아가도 아웃박스에서 다시 보냅니다.

### 한 행의 일생

```
기록됨 (enqueued_at = NULL)
  → 릴레이가 가져감 (enqueued_at = 지금, claim_token = 릴레이 식별값)
  → 처리 완료 (processed_at = 지금)
```

- 처리에 실패하면 `attempts` 가 오르고 `last_error` 에 원인이 남습니다.
- 가져간 지 5분이 지나도 완료되지 않은 이벤트는 유실로 보고 릴레이가 다시 가져갑니다.
- `attempts` 가 10 에 이르면 더 보내지 않습니다. 사람이 원인을 보고 조치합니다.

### 여러 서버가 동시에 릴레이할 때

릴레이는 `UPDATE ... SET claim_token = ? ... ORDER BY id LIMIT n` **한 문장으로** 가져갈 행을 표시합니다. "조회하고 나서 표시"로 나누면 그 사이에 다른 서버가 같은 행을 읽습니다. 한 문장이면 DB 가 행 잠금으로 순서를 세워, 같은 이벤트를 두 서버가 가져가지 않습니다.

## 큐 (BullMQ)

| 설정 | 값 | 이유 |
|---|---|---|
| 재시도 | 5회, 간격 2초 → 4초 → 8초 → 16초 | 일시적 장애는 조금 기다리면 풀린다 |
| 동시 처리 | 5건 | |
| 작업 내용 | `{ outboxId }` 만 | 내용은 DB 에서 읽는다. 큐에는 번호만 |
| 작업 id | `outbox-<id>-<시도 회차>` | 같은 회차의 중복 투입을 걸러낸다 |
| 실패한 작업 | 최근 200개 보관 | 원인 확인용 |

**워커는 웹 서버 안에서 같이 돕니다** (`src/instrumentation.js` 가 서버 시작 시 띄움). Render 무료 플랜에는 백그라운드 워커가 없기 때문입니다. 유료 환경이라면 워커를 별도 프로세스로 떼어, 웹 서버 부하와 무관하게 늘리고 줄일 수 있습니다.

무료 서버가 잠들면 워커도 잠듭니다. 그동안 생긴 이벤트는 아웃박스에 남아 있다가 서버가 깨어날 때 처리됩니다.

## 소비자는 멱등하게

전달 보장은 "적어도 한 번"입니다. 이런 경우 같은 이벤트가 두 번 옵니다.

- 알림을 만든 직후, 완료 표시 직전에 서버가 죽음 → 다시 처리됨
- 큐에서 유실된 줄 알고 다시 보냈는데 원래 것도 살아 있었음

그래서 알림 테이블에 `UNIQUE (event_id, user_id)` 를 두고 `INSERT IGNORE` 로 넣습니다. 같은 이벤트를 몇 번 처리해도 같은 사람에게 알림은 한 번만 생깁니다.

> "정확히 한 번" 전달은 분산 환경에서 보장하기 어렵습니다. 실무에서는 "적어도 한 번 + 멱등한 소비자"로 같은 효과를 냅니다.

## 이벤트 목록

| 이벤트 | 언제 | 알림 받는 사람 |
|---|---|---|
| `trade.created` | 구매 또는 제안 수락 (대금 보관) | 디자이너 |
| `trade.work_started` | 디자이너가 작업 시작 | 구매자 |
| `trade.work_submitted` | 디자이너가 작업 완료 제출 | 구매자 |
| `trade.revision_requested` | 구매자가 수정 요청 | 디자이너 |
| `trade.completed` | 구매확정 (수동/자동) | 디자이너, 구매자 |
| `trade.cancelled` | 취소 (수동/자동) | 구매자, 디자이너 |

거래 이벤트는 `Trade` 엔티티가 상태를 바꾸면서 직접 기록합니다 (`trade.pullEvents()`). 규칙을 아는 곳이 무슨 일이 일어났는지도 가장 잘 알기 때문입니다.

### 소비자 추가하기

`lib/events/eventBus.js` 의 `consumers` 배열에 함수를 하나 붙입니다. 에스크로 코드는 건드리지 않습니다.

```js
const consumers = [handleNotificationEvent, handleSettlementEmail];
```

새 소비자도 같은 이벤트를 두 번 받아도 괜찮게(멱등) 만들어야 합니다.

## 운영 점검

```sql
-- 처리되지 않고 쌓인 이벤트
SELECT id, event_type, aggregate_id, attempts, last_error, enqueued_at, created_at
  FROM outbox_events
 WHERE processed_at IS NULL
 ORDER BY id;

-- 포기한 이벤트 (10회 실패). 원인을 고친 뒤 attempts 를 0 으로 되돌리면 다시 시도한다
SELECT * FROM outbox_events WHERE processed_at IS NULL AND attempts >= 10;
UPDATE outbox_events SET attempts = 0, enqueued_at = NULL WHERE id = ?;
```

서버 로그: `📮 이벤트 처리 시작 (큐 워커 ...)` 또는 `(즉시 처리 ...)` 로 어느 방식인지 알 수 있습니다.
