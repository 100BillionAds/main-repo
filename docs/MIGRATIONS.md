# 스키마 마이그레이션

DB 구조(테이블·컬럼·인덱스)를 바꾸는 방법과, 그 변경이 운영 DB 에 적용되는 방식을 설명합니다.

## 왜 필요한가

이전에는 서버가 뜰 때마다 "전체 스키마를 확인하고 없는 것을 만드는" 함수 하나를 실행했습니다. 이 방식에는 세 가지 문제가 있었습니다.

| 문제 | 설명 |
|---|---|
| 이력이 없다 | 운영 DB 가 지금 어떤 상태인지, 어떤 변경이 언제 들어갔는지 알 수 없습니다. |
| 한 번만 해야 하는 일을 표현하기 어렵다 | 데이터 보정(백필)처럼 "딱 한 번" 실행해야 하는 작업을 매 시작마다 도는 함수에 넣기 위험합니다. |
| 동시 실행에 무방비 | 서버 두 대가 동시에 뜨면 같은 `ALTER TABLE` 을 동시에 실행할 수 있습니다. |

마이그레이션은 스키마 변경을 **번호가 붙은 작은 단위**로 나누고, **어디까지 적용했는지를 DB 에 기록**합니다.

## 용어

| 용어 | 뜻 |
|---|---|
| 마이그레이션 | 스키마 변경 한 묶음. 파일 하나. 예: `0002_add_ai_requests` |
| 적용 기록 | `schema_migrations` 테이블의 한 행. "이 마이그레이션을 이 DB 에 실행했다" |
| 체크섬 | 마이그레이션 내용의 SHA-256. 적용 당시의 내용과 지금 코드가 같은지 비교하는 데 씁니다. |
| 베이스라인 | `0001_baseline`. 마이그레이션 체계를 도입한 시점의 전체 스키마. |
| 대기 중(pending) | 코드에는 있지만 이 DB 에는 아직 적용되지 않은 마이그레이션 |

## 구성

```
10badv/src/lib/migrations/
├── migrator.js        # 러너: 잠금, 검증, 실행, 기록
├── index.js           # 마이그레이션 목록 (실행 순서)
└── 0001_baseline.js   # 마이그레이션 (데이터)
```

서버가 시작되면 `src/instrumentation.js` → `initializeDatabase()` → `runMigrations()` 순으로 호출됩니다.

## 실행 흐름

1. **잠금** — `GET_LOCK('migrate:<DB이름>', 60)` 으로 DB 수준 잠금을 잡습니다. 서버가 여러 대여도 한 대만 진행하고, 나머지는 기다립니다. 잠금은 커넥션에 묶여 있어, 서버가 죽으면 자동으로 풀립니다.
2. **기록 읽기** — 잠금을 잡은 뒤에 `schema_migrations` 를 읽습니다. 기다리는 동안 다른 서버가 적용을 끝냈을 수 있기 때문입니다.
3. **검증** — 아래 중 하나라도 해당하면 아무것도 실행하지 않고 멈춥니다.
4. **적용** — 대기 중인 것만 번호 순서대로 실행하고, 하나가 끝날 때마다 기록합니다.
5. **잠금 해제**

| 오류 코드 | 상황 | 대응 |
|---|---|---|
| `CHECKSUM_MISMATCH` | 이미 적용된 마이그레이션 파일이 수정됨 | 수정을 되돌리고, 변경은 새 마이그레이션으로 추가 |
| `MISSING_MIGRATION` | DB 에 적용된 것이 코드에 없음 | DB 보다 오래된 코드를 배포한 경우. 최신 코드로 배포 |
| `OUT_OF_ORDER` | 새 마이그레이션 번호가 이미 적용된 번호보다 앞섬 | 가장 큰 번호로 다시 매기기 (브랜치 병합 때 주로 발생) |
| `LOCK_TIMEOUT` | 60초 안에 잠금을 얻지 못함 | 다른 서버의 마이그레이션이 끝났는지 확인 후 재시작 |
| `STEP_FAILED` | SQL 실행 실패 | 로그의 단계 번호와 원인을 보고 수정. 아래 "실패했을 때" 참고 |

실패하면 서버 로그에 `데이터베이스 마이그레이션 실패` 가 남습니다. 서버 자체는 계속 뜨지만, 새 스키마가 필요한 기능은 동작하지 않습니다.

## 새 마이그레이션 추가하기

`users` 에 닉네임 컬럼을 추가하는 예입니다.

**1. 파일을 만듭니다** — `src/lib/migrations/0002_add_user_nickname.js`

```js
const migration = {
  id: '0002_add_user_nickname',
  description: '사용자 닉네임 컬럼 추가',
  steps: [
    { addColumn: ['users', 'nickname', 'VARCHAR(50) NULL'] },
    { addIndex: ['users', 'idx_users_nickname', 'nickname'] },
  ],
};

export default migration;
```

**2. 목록 맨 끝에 추가합니다** — `src/lib/migrations/index.js`

```js
import baseline from './0001_baseline.js';
import addUserNickname from './0002_add_user_nickname.js';

const migrations = [baseline, addUserNickname];
```

**3. 문서를 고칩니다** — [ERD.md](./ERD.md) 의 테이블 설명.

배포하면 서버가 뜨면서 `0002` 만 실행합니다.

### step 종류

| 형태 | 동작 | 다시 실행해도 안전한가 |
|---|---|---|
| `'SQL 문자열'` | 그대로 실행 | 작성자가 보장해야 함 (`CREATE TABLE IF NOT EXISTS` 등) |
| `{ addColumn: [테이블, 컬럼, 정의], onAdded: [SQL...] }` | 컬럼이 없을 때만 추가. **추가했을 때만** `onAdded` 실행 (백필용) | 예 |
| `{ addIndex: [테이블, 인덱스명, 컬럼들], unique: true }` | 인덱스가 없을 때만 생성 | 예 |

## 규칙

1. **적용된 마이그레이션은 고치지 않는다.** 오타 하나라도 새 마이그레이션으로 고칩니다. (들여쓰기·개행만 바꾸는 것은 체크섬에 영향이 없습니다.)
2. **번호는 항상 가장 큰 번호 다음.** 4자리 숫자 + `_` + 영문 소문자 설명.
3. **다시 실행해도 안전하게 쓴다.** 아래 "실패했을 때" 때문입니다.
4. **삭제·이름 변경은 두 번에 나눠 배포한다.** 컬럼을 지우는 마이그레이션과 그 컬럼을 쓰지 않는 코드를 한 번에 배포하면, 배포 중 잠깐 옛 코드가 없는 컬럼을 읽습니다. 먼저 코드에서 사용을 없애 배포하고, 다음 배포에서 컬럼을 지웁니다.
5. **큰 테이블의 백필은 마이그레이션에 넣지 않는다.** 서버 시작이 그만큼 늦어집니다. 별도 작업으로 돌립니다.

## 실패했을 때

MySQL 과 TiDB 는 `CREATE TABLE`, `ALTER TABLE` 같은 DDL 을 **트랜잭션으로 되돌릴 수 없습니다**. 마이그레이션이 3단계 중 2단계에서 실패하면 1단계는 이미 반영된 채로 남습니다.

러너는 이렇게 동작합니다.

- 실패한 마이그레이션은 **기록하지 않습니다**.
- 다음 시작 때 그 마이그레이션을 **1단계부터 다시** 시도합니다.

그래서 각 step 이 "이미 되어 있으면 건너뛰는" 방식이어야 합니다. `addColumn`, `addIndex` 가 존재 여부를 먼저 확인하는 이유입니다.

## 되돌리기(롤백)

"down" 마이그레이션은 두지 않았습니다. 되돌리는 변경도 **앞으로 가는 새 마이그레이션**으로 작성합니다 (예: `0003_drop_user_nickname`). 운영 데이터가 있는 DB 에서 자동 롤백은 데이터를 잃기 쉬워, 사람이 의도를 갖고 작성하는 편이 안전합니다.

## 상태 확인

```sql
SELECT id, description, execution_ms, applied_at FROM schema_migrations ORDER BY id;
```

코드에서는 `getMigrationStatus()` (`src/lib/db.js`) 가 마이그레이션별 적용 여부와 체크섬 일치 여부를 돌려줍니다.

## 기존 DB 는 어떻게 되나

`0001_baseline` 의 모든 단계는 "없으면 만든다" 입니다.

| DB 상태 | 결과 |
|---|---|
| 빈 DB | 전체 스키마를 만들고 기록 |
| 최신 스키마가 이미 있는 DB (현재 운영) | 바뀌는 것 없이 기록만 남김 |
| 에스크로 도입 전의 옛 스키마 | 누락된 컬럼·인덱스를 보강하고, 기존 거래의 에스크로 상태를 한 번 백필 |
